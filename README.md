1. [Whatever][Backend/Frontend] Дополнительные файлы в карточке сервиса
Цель
Добавить в карточку сервиса Whatever возможность хранения и просмотра дополнительных файлов, относящихся к сервису.
Что требуется
•	Добавить в карточку сервиса раздел для дополнительных файлов. 
•	Реализовать возможность загрузки файлов, связанных с сервисом. 
•	Реализовать просмотр списка ранее загруженных файлов. 
•	Предусмотреть возможность скачивания файлов. 
•	Предусмотреть хранение служебной информации о файле: название, дата загрузки, автор загрузки.
•	Использовать для хранения файлов файлохранилище MinIO вместо существующего FTP. 
•	Ограничить загрузку и управление файлами существующими правами доступа Whatever. 
Критерии приемки
•	Пользователь с необходимыми правами может загрузить дополнительный файл в карточку сервиса. 
•	Загруженный файл отображается в карточке соответствующего сервиса. 
•	Пользователь может скачать ранее загруженный файл. 
•	Файлы одного сервиса не отображаются в карточках других сервисов. 
•	После перезапуска приложения информация о загруженных файлах сохраняется. 
•	Реализованы состояния загрузки, ошибки загрузки и отсутствия файлов. 
Definition of Done
•	Backend-часть реализована в whatever-api. 
•	Frontend-часть реализована в whatever-web. 
•	Хранилище файлов настроено и используется приложением. 
•	API описан в OpenAPI. 
•	Тесты, production build и обязательные CI jobs проходят. 
•	Frontend проверен с фактическим backend API.

2. [Whatever][Backend/Frontend] История последних pipeline в карточке сервиса
Цель
Расширить раздел «Последний pipeline» в карточке сервиса и отображать историю заявок, по которым выполнялось обновление сервиса.
Что требуется
•	Отображать в карточке сервиса последние 5 заявок, связанных с обновлением данного сервиса. 
•	Для каждой заявки отображать: 
o	номер заявки; 
o	ссылку на соответствующую ветку в GIT; 
o	ссылку на заявку в BPM. 
•	Добавить действие «Показать все обновления». 
•	Реализовать отдельное представление полного списка заявок, по которым обновлялся сервис. 
•	Определять связь между сервисом, pipeline и заявкой на основании. 
•	Получать ссылки на GIT и BPM. 
•	Для полного списка предусмотреть сортировку по дате обновления и пагинацию. 
Критерии приемки
•	В разделе «Последний pipeline» отображаются до 5 последних заявок сервиса. 
•	Для каждой записи доступны переходы в GIT и BPM. 
•	По кнопке «Показать все обновления» пользователь может просмотреть полную историю обновлений сервиса. 
•	История отображается только для выбранного сервиса. 
•	Последние записи отображаются в порядке от новых к старым. 
•	При отсутствии истории отображается соответствующее состояние. 
Definition of Done
•	Необходимые изменения реализованы в whatever-api и whatever-web. 
•	Интеграция с источником данных pipeline/GIT/BPM реализована. 
•	API описан в OpenAPI. 
•	Тесты, production build и обязательные CI jobs проходят. 
•	Frontend проверен с фактическими данными backend.

3. [Whatever][Frontend/Backend] Каталог систем и статистика по типам систем
Цель
Переименовать раздел «Каталог сервисов» в «Каталог систем» и добавить сводную статистику по типам информационных систем.
Что требуется
•	Переименовать пользовательский раздел «Каталог сервисов» в «Каталог систем». 
•	В верхней части каталога добавить информационные карточки со следующими показателями: 
o	Всего систем; 
o	Всего внешних; 
o	Всего внутренних; 
o	Всего вспомогательных; 
o	Всего интеграционных. 
•	Не отображать карточку категории, если в соответствующей категории отсутствуют системы. 
•	Рассчитывать показатели на основании типа информационной системы. 
•	Добавить/использовать типы систем: 
o	Внешняя; 
o	Внутренняя; 
o	Вспомогательная; 
o	Интеграционная. 
•	Получать статистику через существующий API либо добавить отдельный endpoint. 
Критерии приемки
•	В интерфейсе раздел называется «Каталог систем». 
•	В верхней части страницы отображается общее количество систем. 
•	Для каждой непустой категории отображается отдельный счетчик. 
•	Категории с количеством 0 не отображаются. 
•	Значения счетчиков соответствуют фактическим данным каталога. 
•	После изменения типа или количества систем статистика отображает актуальные значения. 
Definition of Done
•	Изменения реализованы в whatever-web. 
•	Необходимые изменения API реализованы в whatever-api. 
•	Тип системы хранится в PostgreSQL. 
•	Тесты, production build и обязательные CI jobs проходят. 
•	Frontend проверен с фактическим backend API.

4. [Whatever][Backend/Frontend] Структурирование справочника сотрудников
Цель
Расширить справочник «Сотрудники», структурировать сотрудников по организационной структуре и добавить дополнительную техническую информацию в карточку сотрудника.
Что требуется
•	Структурировать сотрудников по департаментам и управлениям. 
•	Добавить в карточку сотрудника следующие поля: 
o	Должность; 
o	Тип работника: штат / внештат; 
o	Режим работы: гибридный / удаленный; 
o	Имя виртуальной машины; 
o	Сервер, на котором размещена виртуальная машина. 
•	Реализовать хранение новых данных в PostgreSQL. 
•	Добавить API для получения и изменения новых данных. 
•	Добавить отображение организационной структуры сотрудников в интерфейсе. 
•	Использовать существующие данные о департаментах и управлениях. 
•	Предусмотреть поиск/фильтрацию сотрудников по департаменту и управлению. 
Критерии приемки
•	Сотрудники сгруппированы или доступны для просмотра по департаментам и управлениям. 
•	В карточке сотрудника отображаются новые поля. 
•	Пользователь с соответствующими правами может редактировать новые данные. 
•	Тип работника и режим работы выбираются из заданных значений. 
•	Данные после сохранения корректно отображаются при повторном открытии карточки. 
•	При отсутствии виртуальной машины или сервера соответствующие поля могут оставаться пустыми. 
Definition of Done
•	Изменения структуры данных реализованы в whatever-api. 
•	Изменения интерфейса реализованы в whatever-web. 
•	Миграции PostgreSQL подготовлены. 
•	API описан в OpenAPI. 
•	Тесты, production build и обязательные CI jobs проходят. 
•	Frontend проверен с фактическим backend API.

5. [Whatever][Backend/Frontend] Расширение карточки информационной системы
Цель
Расширить карточку информационной системы Whatever дополнительными техническими и организационными параметрами.
Что требуется
•	Добавить в модель информационной системы следующие данные: 
o	Тип информационной системы: Внешняя / Внутренняя / Вспомогательная / Интеграционная; 
o	Наименование департамента; 
o	Наименование системы; 
o	Описание системы; 
o	Адрес ресурса TEST; 
o	Адрес ресурса PROD; 
o	Frontend: Angular / Vue.js / React / Flutter / Swagger / отсутствует; 
o	Версия Frontend; 
o	Backend: .NET Framework / .NET Core / .NET / Java /; 
o	Версия Backend ~; 
o	Файловое хранилище: S3 / MinIO / File Server / отсутствует; 
o	СУБД: MS SQL / PostgreSQL / Oracle /; 
o	Самописная система: Да / Нет; 
o	Ответственный за систему / бизнес-владелец: подразделение. 
•	Использовать справочники для значений, которые должны выбираться из фиксированного набора. 
•	Добавить необходимые поля в API создания, просмотра и изменения системы. 
•	Добавить соответствующие элементы управления в карточку системы. 
•	Сохранить обратную совместимость существующих карточек систем. 
•	Для необязательных параметров разрешить отсутствие значения. 
Критерии приемки
•	Все указанные параметры доступны в карточке системы. 
•	Пользователь с необходимыми правами может изменять параметры. 
•	После сохранения данные сохраняются в PostgreSQL и корректно возвращаются API. 
•	Тип информационной системы ограничен четырьмя предусмотренными категориями. 
•	Поля TEST и PROD позволяют хранить URL соответствующих сред. 
•	Для отсутствующих технологий или ресурсов можно выбрать/указать «отсутствует». 
•	Существующие системы продолжают корректно открываться после обновления модели данных. 
Definition of Done
•	Изменения модели и миграции реализованы в whatever-api. 
•	API создания/изменения/просмотра системы обновлен и описан в OpenAPI. 
•	UI карточки системы обновлен в whatever-web. 
•	Тесты и обязательные CI jobs проходят. 
•	Production build проходит. 
•	Frontend проверен с фактическим backend API.

6. [Whatever][Frontend/Backend] Разделение ресурсов Dashboard по типам информационных систем
Цель
Разделить отображаемые на Dashboard ресурсы по типам информационных систем для более понятной классификации систем Whatever.
Что требуется
•	Использовать четыре типа информационных систем: 
o	Внешние системы — системы и сервисы для взаимодействия с клиентами, партнерами и внешними пользователями; 
o	Внутренние системы — системы, используемые сотрудниками Банка для выполнения внутренних бизнес-процессов; 
o	Вспомогательные системы — системы поддержки основных процессов, администрирования, мониторинга, аналитики и других вспомогательных функций; 
o	Интеграционные системы — платформы и компоненты для обмена данными между информационными системами. 
•	Разделить существующие ресурсы Dashboard по указанным категориям. 
•	Использовать значение типа информационной системы из карточки системы. 
•	Для каждой категории отображать относящиеся к ней системы/ресурсы. 
•	Не отображать пустую категорию. 
•	Сохранить существующие возможности перехода из Dashboard к соответствующей системе/сервису. 
•	Обновить статистику Dashboard с учетом нового разделения. 
Критерии приемки
•	Все ресурсы Dashboard распределяются в соответствии с типом информационной системы. 
•	Внешние, внутренние, вспомогательные и интеграционные системы визуально разделены. 
•	Система отображается только в своей категории. 
•	Изменение типа системы отражается на Dashboard. 
•	Существующие переходы из Dashboard к карточкам систем продолжают работать. 
Definition of Done
•	Изменения Dashboard реализованы в whatever-web. 
•	Backend предоставляет тип системы в необходимом API. 
•	При необходимости API Dashboard обновлен в whatever-api. 
•	Тесты, production build и обязательные CI jobs проходят. 
•	Frontend проверен с фактическим backend API.
